# macOS camera-extension probe — results

Run date: 2026-08-07
Plan reference: `CAMERA_BUILD_PLAN.md` §18 step 2, §8.1

## Machine

| Field | Value |
|---|---|
| macOS | 26.5.1 (build 25F80) |
| Hardware | Apple Silicon (MacBook Air) |
| Xcode | 26.6 (17F113) |
| Swift | 6.3.3 |
| SIP | **enabled** |
| Code-signing identities available | **0** (`security find-identity -v -p codesigning`) |
| Apple ID in Xcode | none configured (no provisioning profiles present) |

## Verdict

**A Core Media I/O camera extension cannot be installed on this Mac with a
free Apple ID while SIP is enabled.** Not "is awkward" — cannot. Both routes
are closed, and they are closed by two different mechanisms.

§8.1 predicted the entitlement wall. What it did not predict is that
developer mode, which it treats as the free workaround, is itself gated behind
disabling SIP on current macOS.

## What was measured

### 1. Ad-hoc signature that *claims* the entitlement → killed at launch

The app was signed ad-hoc (`codesign --sign -`) with
`com.apple.developer.system-extension.install` in its entitlements.

```
$ "Meo Camera Probe.app/Contents/MacOS/MeoCameraProbe" --cli-install
EXIT=137
```

Exit 137 is SIGKILL. The process never reached its own code. AMFI kills a
binary that claims a restricted entitlement without a provisioning profile
authorising it.

This is worth stating precisely because it is worse than a failed install: an
app that merely *asks* for this entitlement without a paid account will not
launch at all.

### 2. Ad-hoc signature without the entitlement → runs, refuses to install

Same bundle, re-signed with no entitlements:

```
[2026-08-06T18:56:43Z] Requesting activation of com.meo.camera.probe.extension
[2026-08-06T18:56:43Z] FAILED: OSSystemExtensionErrorDomain code 2 —
                       Missing entitlement com.apple.developer.system-extension.install
```

`OSSystemExtensionError.missingEntitlement`. Exactly the §8.1 prediction.

### 3. The `/Applications` requirement is not the cause

Ruled out as a confounder. The same no-entitlement build was copied to
`/Applications`, its signature re-verified there (`codesign --verify --deep
--strict` passed), and run again. Identical error, same code 2. The location
rule is real but it is not what is blocking this — the entitlement check fires
first.

### 4. Developer mode is unavailable while SIP is on

```
$ systemextensionsctl developer on
At this time, this tool cannot be used if System Integrity Protection is enabled.
This limitation will be removed in the near future.
Please remember to re-enable System Integrity Protection!
```

This is the finding that changes the plan. §8.1's primary macOS path is
"clone, build, `systemextensionsctl developer on`, install, use". On macOS
26.5.1 that command refuses to run until the user boots into Recovery and
disables System Integrity Protection.

### Extension bundle itself is fine

Not the bottleneck, and worth recording so nobody re-litigates it:

- The extension compiles clean against CoreMediaIO on the 13.0 deployment
  target (§3's floor is 12.3).
- Both bundles assemble, sign ad-hoc, and pass `codesign --verify --deep
  --strict`, including after being copied to `/Applications`.
- `TeamIdentifier=not set`, which is the free-account condition being tested.

The extension was never loaded, so its frame path is **unverified**. Colour
bars, NV12 layout, timing, and consumer visibility are all still unknown.

## Not tested, and why

| Case | Why not | How to close it |
|---|---|---|
| **Personal-team (free Apple ID) signature** | No Apple ID is configured in Xcode on this machine and there are zero code-signing identities. | Sign into Xcode with an Apple ID, re-run `./build.sh "Apple Development: <name>"`. Expected to fail the same way — Apple does not offer the System Extension capability to free personal teams — but it is one command and it is the last free option, so it should be measured rather than assumed. |
| **Developer mode + SIP disabled** | Requires a Recovery-mode reboot and a deliberate weakening of the machine's security. Not something to do without the maintainer choosing it. | See below. |
| **Visibility to Chrome / Zoom / Safari** | Blocked — the extension never installed. | Only reachable after one of the above works. |

## What this does to the plan

§8.1 says: "The answer decides whether the macOS path is viable at all."
The answer is in, and it is worse than the plan assumed.

The plan's stated primary macOS path — build from source, enable developer
mode, SIP intact — **does not exist on current macOS**. What is left:

1. **Disable SIP.** Free, works, and asks every user to boot into Recovery and
   turn off a core security feature to use a webcam app. For a tool whose
   pitch is "free, private, local-only", telling users to disable SIP is a
   hard sell and arguably an irresponsible one. Meo Mic asks users to click
   past Gatekeeper once; this is a different order of ask.
2. **Pay for a Developer Program membership.** Violates C1 outright.
3. **Ship macOS Camera later, or not at all**, and put Windows first.

Option 3 is the one that fits the constraints without compromising them, and
it also happens to be the answer to §19's "which desktop platform is finished
first in Milestone 5". It should be Windows — not because Windows looked
easier, but because macOS is currently blocked by a policy Meo cannot
negotiate with.

This does not touch Meo Mic. That ships a plain unsigned app with no system
extension and is unaffected.

## Recommended next steps

1. Sign into Xcode with a free Apple ID and re-run with a personal-team
   identity, to close the last free option on the record rather than by
   inference.
2. Treat the macOS camera receiver as **blocked**, not cancelled, and write it
   into `adr/0004-macos-distribution-reality.md`.
3. Re-order Milestone 5 to Windows-first.
4. Do not write macOS camera UI until this is unblocked. §12's Milestone 0
   gate — "no UI polish begins until frames reach at least one real virtual
   camera" — now has real force on this platform.
5. Correct §8.1 and §16 of the plan. They currently promise a build-from-source
   macOS path that current macOS does not permit, and §16.1's honesty
   requirements apply to the plan itself, not only to the README.
